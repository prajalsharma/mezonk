## Findings

[75] **1. A curator cannot cancel an approval it signed**

`MezonkMarkets._consumeApproval` · Confidence: 75 · seen in 1/3 runs · NEW

**Description**
No function marks an unused nonce as used and the deadline has no upper bound, so a creator publishes a market from an approval the curator withdrew.

**Fix**

```diff
+    /// @notice Voids an approval the caller signed but no longer stands behind. The owner may void any.
+    function cancelApproval(bytes32 nonce) external {
+        if (!isCurator[msg.sender] && msg.sender != owner()) revert NotCurator();
+        approvalUsed[nonce] = true;
+        emit ApprovalCancelled(msg.sender, nonce);
+    }
```

## Leads

_Vulnerability trails with concrete code smells where the full exploit path could not be completed in one analysis pass. These are not false positives — they are high-signal leads for manual review. Not scored._

- **The deploy script makes the script sender the owner** — `Deploy.run` · seen in 1/3 runs · NEW — Code smells: new MezonkMarkets(IERC20(musd), msg.sender, c); with several signers and no --sender Foundry's default sender is msg.sender — A run with several loaded signers makes Foundry's default sender the owner, and the later setResolver call reverts in simulation. We did not check this against the user's forge version.
- **The deploy script truncates env values without a check** — `Deploy.run` · seen in 2/3 runs · NEW — Code smells: uint16(vm.envOr("FEE_BPS", …)), uint32(…) and uint128(…) downcasts; FEE_BPS=65636 becomes 100 and PROPOSER_BOND=2^128 becomes 0 — An operator typo deploys a different fee, window or bond than the env file states. Only the operator can trigger it.
- **Sells of the expensive side revert when the other pool is near zero** — `FPMMMath.sell` · seen in 3/3 runs · NEW — Code smells: `if (grossOut == 0 || grossOut >= poolOther) revert InsufficientPool()` — When buys push one pool side close to zero, sellers of the other side get a revert until closeTime. That state needs a deposit near poolYes·poolNo, so we found no realistic input that reaches it.
- **The creator gets back part of every fee it pays in its own market** — `MezonkMarkets._accrueFee` · seen in 1/3 runs · NEW — Code smells: the creator may trade in its own market and _accrueFee credits the creator share of each fee to m.creatorFees — A creator inflates the trade volume of its own market at half the fee cost. We did not find a direct loss to other users.
- **Nothing stops the publisher from being the market's resolver** — `MezonkMarkets._consumeApproval` · seen in 2/3 runs · NEW — Code smells: the function checks curator != msg.sender but not p.resolver != msg.sender; at 9500 bps the creator holds 18/19 of the liquidity outright — A wallet that is both creator and resolver proposes the outcome that pays its own pool, and only the curator's review stops it. We did not show that a curator signs such a market.
- **A curator EOA with code cannot sign approvals** — `MezonkMarkets._consumeApproval` · seen in 2/3 runs · NEW — Code smells: SignatureChecker skips ECDSA whenever curator.code.length != 0 — A curator EOA that delegates with EIP-7702 can no longer approve unless its delegate implements isValidSignature. Mezo targets london, so we did not confirm that 7702 is live there.
- **An ERC-1271 curator controlled by the creator passes the self-approval check** — `MezonkMarkets._consumeApproval` · seen in 3/3 runs · NEW — Code smells: SelfApproval compares curator == msg.sender only — A creator that signs for an ERC-1271 curator contract approves and publishes its own market. This needs the owner to approve such a curator contract.
- **All curators share one approval nonce space** — `MezonkMarkets._consumeApproval` · seen in 3/3 runs · NEW — Code smells: approvalUsed is keyed by nonce only, not by (curator, nonce) — Two curators that sign the same nonce block each other. The backend derives the nonce from the proposal id and version, so we did not find a way for an attacker to choose a colliding nonce.
- **The curator signature does not cover the opening odds, the seed or the live config** — `MezonkMarkets._consumeApproval` · seen in 3/3 runs · NEW — Code smells: MARKET_APPROVAL_TYPEHASH omits initialYesProbBps and initialLiquidity; the arbitrator, fee, bonds and windows come from the live config at publish time — The creator alone sets the first price traders see and the seed size, and the owner can change the config between the signature and the publication. We found no third party who loses tokens.
- **The owner cannot replace the arbitrator on live markets** — `MezonkMarkets._initMarket` · seen in 1/3 runs · NEW — Code smells: m.arbitrator is copied from the config at creation and no function changes it — A lost or stolen arbitrator key controls every open dispute until those markets settle. We found no path that uses this without the key.
- **Nothing stops the market creator from being the arbitrator** — `MezonkMarkets._initMarket` · seen in 1/3 runs · NEW — Code smells: m.arbitrator comes from the global config and createMarket never compares msg.sender with it — A creator that is also the arbitrator rules a dispute for its own pool position. This needs the owner to set that config.
- **The owner can set a zero proposer bond** — `MezonkMarkets._setConfig` · seen in 2/3 runs · NEW — Code smells: _setConfig rejects disputeBond == 0 but accepts proposerBond == 0 — With a zero proposer bond a resolver proposes a wrong outcome at no cost and a correct disputer earns nothing. This needs an owner config change or an operator typo.
- **The disputer wins both bonds even when it argued for a different wrong outcome** — `MezonkMarkets.arbitrate` · seen in 3/3 runs · NEW — Code smells: winner = outcome == m.proposedOutcome ? m.resolver : m.disputer; dispute records no claimed outcome — When the proposal is Yes, the disputer argues No and the arbitrator rules Invalid, the disputer still takes both bonds. The resolver did propose a wrong outcome, so we did not name a victim who loses more than the design intends.
- **Buys under 100 wei pay no fee** — `MezonkMarkets.buy` · seen in 2/3 runs · NEW — Code smells: fee = (amountIn * m.feeBps) / BPS rounds down — A buyer pays no fee on trades under 100 wei. Gas cost makes this unprofitable.
- **No role can close trading before closeTime once the result is known** — `MezonkMarkets.buy` · seen in 1/3 runs · NEW — Code smells: trading stops only at closeTime and proposeOutcome requires Stage.Closed — Traders who learn the result before closeTime buy the winning side at the old pool price, and the creator's pool pays them. The market rules are meant to close at or before the event, which we did not verify per market.
- **Any caller delays settlement of any market for 25 MUSD** — `MezonkMarkets.dispute` · seen in 3/3 runs · NEW — Code smells: disputeBond is a fixed config amount and one dispute moves settlement back by up to arbitrationWindow — A caller pays 25 MUSD to stop redemption for every holder of a market of any size for up to seven days, and loses the bond only if the arbitrator rules in time.
- **A late arbitrator makes a dispute free and pays the losing side 0.5 per share** — `MezonkMarkets.finalize` · seen in 3/3 runs · NEW — Code smells: the Disputed branch refunds the full disputeBond and settles Invalid; one arbitrator serves every market, so an attacker can open disputes on many markets at once to exceed its seven-day capacity — A holder of the losing side disputes a correct proposal for 25 MUSD and gets the bond back and 0.5 per share if the arbitrator misses its window. We did not prove that the arbitrator misses it.
- **The proposer bond does not scale with the market** — `MezonkMarkets.proposeOutcome` · seen in 1/3 runs · NEW — Code smells: proposerBond is a fixed config amount and the resolver can trade in the markets it resolves — A resolver trades against a large market and proposes the wrong outcome, and it risks only a fixed 25 MUSD bond if a dispute arrives. We did not measure how often one arrives.
- **The resolver proposes Invalid on a market with a clear answer** — `MezonkMarkets.proposeOutcome` · seen in 1/3 runs · NEW — Code smells: proposeOutcome accepts Outcome.Invalid for any market and the resolver may trade in the markets it resolves — A resolver buys cheap shares and proposes Invalid, so it collects 0.5 per share unless somebody disputes within the challenge window. This is the active form of the silent-resolver finding.
- **A revoked resolver keeps proposing on its existing markets** — `MezonkMarkets.proposeOutcome` · seen in 3/3 runs · NEW — Code smells: proposeOutcome checks only msg.sender == m.resolver and nothing replaces m.resolver on a live market — The owner cannot stop a revoked or compromised resolver on markets that already exist, so a dispute is the only defense.
- **Trades under 100 wei pay no fee** — `MezonkMarkets.sell` · seen in 3/3 runs · NEW — Code smells: fee = (gross * m.feeBps) / BPS rounds down — A trader who splits a trade into parts below 100 wei pays no fee. Gas costs more than the fee saved, so we found no profitable path.
- **A holder of both sides cannot merge them into collateral before settlement** — `MezonkMarkets.sell` · seen in 1/3 runs · NEW — Code smells: no function burns one YES plus one NO for one collateral unit; during a pause the holder cannot exit at all — A user who holds both YES and NO exits only through sell, with the fee and the price impact. We did not find a way for a third party to take value from this.
- **The role setters repeat none of the deploy-script separation checks** — `MezonkMarkets.setCurator` · seen in 1/3 runs · NEW — Code smells: Deploy.s.sol requires curator != resolver, curator != arbitrator and creator != curator; setCurator, setCreator and setResolver check none of these, and nothing stops the owner from naming itself curator — The owner can give one wallet the curator, creator and arbitrator roles, so that wallet publishes a market and rules on its disputes with no independent review. This needs an owner action.
- **The contract checks resolver and arbitrator separation only in the deploy script** — `MezonkMarkets.setResolver` · seen in 2/3 runs · NEW — Code smells: setResolver, _setConfig and createMarket never compare the resolver with config.arbitrator; docs/MARKET_GOVERNANCE.md says the pair is enforced — The owner can later approve the arbitrator as a resolver, and that one address then proposes, rules on disputes against itself and keeps disputer bonds. This needs an owner action.
